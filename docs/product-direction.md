## 0. 结论（先给答案）

| 项 | 结论 |
|---|---|
| **推荐主线** | **「受治理 Agent 运行时」的开发者底座 + 企业治理增值**：核心 Apache-2.0 开源建信任与生态，治理/合规/审计能力做成企业版与托管交付 |
| **一句话理由** | 12 包底座里真正稀缺、且已被工程验证的不是「又一个 agent loop」，而是**把 沙箱 × 审批 × 审计 × 可恢复 做成产品级闭环**；而这正是 2026 企业侧规模化落地的首要阻塞项 |
| **产品形态定位** | **底座 SDK（L0，唯一一等公民）**：`packages/*` 12 包 + 治理能力导出（L1）；`examples/`（CLI/Web）与 `deploy/` **降级为验证载体，不作为产品线**（判定见 `docs/base-convergence.md`）；**桌面端已自底座侧移入产品侧**，作为产品形态候选另行评估（§4 末条） |
| **M7 第一批（建议）** | **M7-1** 成本与上下文治理（token 计量/压缩）、**M7-2** 可观测与合规导出（traceId/OTEL/审计导出）、**M7-3** 策略工程化（声明式规则 + 内联测试）、**M7-6** 工具规模治理（`tool_search` + MCP 只读资源）；**审批体验（M7-4）按 §5 降级为验证载体增强，不占关键路径**。执行清单见 `docs/m7-base-governance.md` |
| **明确不做（现阶段）** | 垂直行业 Agent 应用（与底座资产错位、需领域数据与交付能力）。**桌面形态已自本条移出**：底座不再判定其立项与否，改由产品侧评估（§4 末条、§8-3） |

## 1. 资产盘点：我们真正拥有什么

| 资产 | 成熟度 | 市场稀缺度 | 可产品化程度 |
|---|---|---|---|
| 沙箱 × 审批二维治理（`SandboxMode` 三档 + `PermissionManager` ask/`always` 白名单 + 审批审计落库） | 生产级（有自动化测试、生产默认预设） | **高**：多数框架只给 hook，不给完整决策链 | 直接：治理控制台 / 策略中心 |
| 步级 Checkpoint + 工具指纹校验续跑（`computeToolsHash`/`resume`） | 生产级（transcript 等价已验证） | 中高：框架层多为「重试」而非「可恢复」 | 直接：长任务可靠性卖点 |
| 事件总线 + 结构化日志 + 脱敏（密钥永不进事件/日志/diff） | 生产级（P3 加固含循环引用与厂商 token 形态） | 中：合规场景刚需 | 直接：审计与可观测导出 |
| 12 包单向无环 SDK（ESM、零运行时依赖、API 面冻结 + `check:api`） | 发布就绪（canary 实装验证通过） | 中：同类多为单体框架，可单独消费的包少 | 直接：npm 生态入口 |
| MCP client（stdio + HTTP，含 SSRF 防护与 env 最小化） | 生产级 | 中 | 直接：工具生态接入 |
| Web/Desktop 控制台（SSE 事件流、审批卡片、diff、artifact、续跑） | demo 级 | 中 | **需升级**：从演示面 → 运维治理台 |
| 配置分层 + 特性开关（`loadConfig`，env > 默认 + 可读错误） | 生产级 | 低（基础能力） | 间接：企业交付的配置基线 |

**结论**：资产结构是**「治理纵深」强、「应用表层」弱**。产品方向应顺着强项走，而不是补短板去和应用型团队拼场景。

## 2. 市场位置（2026-09 定性）

- **框架层极度拥挤**：LangGraph、OpenAI Agents SDK、CrewAI、AutoGen、Google ADK、Claude Agent SDK 等已在编排/多 agent/生态上占据心智；同代 TS 运行层还有 `deepseek-harness`（插件化 harness，MIT，developer preview，明确声明将有破坏性变更）。
- **饱和的是「能跑」，稀缺的是「管得住」**：行业信号一致指向同一组阻塞项——**权限边界、审计留痕、成本可见、失败可恢复、模型可替换**，这些恰是「框架 demo 到生产」之间掉链子的地方。
- **我们的相对位置**：在「编排表达力」上不在第一梯队，也不应去竞争；在「**执行治理链路的完备度 + 可移植的零依赖包结构 + 模型中立**」上有明确差异化——这是**基础设施位**，而非应用位。
- **窗口判断**：治理能力正在从「加分项」变成「准入项」，但尚无事实标准；此刻把治理做成**可复用、可导出、可审计的开发者资产**，比晚两年补做更有机会。反过来，若转去做垂直应用，现有治理资产只能当内部脚手架，浪费最大的一块投入。

## 3. 方向候选与评估

| 方向 | 描述 | 与现有资产契合 | 差异化强度 | 投入 | 变现周期 | 主要风险 |
|---|---|---|---|---|---|---|
| **A. 开源底座 + 企业治理增值**（推荐） | Apache-2.0 开源 12 包 SDK；企业版/团队版提供审计导出、策略中心、配额与多租户、SSO、SLA 支持 | **极高**（几乎全部资产直接复用） | 高（治理闭环 + 模型中立 + 包级可消费） | 中 | 中（需先有企业触达） | 开源获客与信任建立慢；open-core 边界需谨慎设计 |
| B. 企业私有化「受治理 Agent 运行时」平台 | 以控制台为核心交付私有化部署：策略配置、审批工作台、审计报表、配额 | 高（控制台需从 demo 升级） | 高（合规交付视角，而非框架视角） | 中高（含交付与实施） | 中（项目制/年费） | 需行业方案与实施能力；单点客户依赖 |
| C. 垂直 Agent 应用（代码/运维/数据分析） | 面向终端用户的场景化 Agent 产品 | 中（引擎可复用，治理资产仅内部用） | 低-中（红海、需领域数据） | 高 | 长 | 与巨头正面竞争；底座投入被浪费 |
| D. 桌面形态（个人助手 / 桌面工作台） | 分发 .app/.dmg，或在已有桌面客户端（ACP 客户端）内呈现，面向个人/团队的本地 Agent 体验 | 中（`examples/desktop-tauri/` 代码与 P5 脚本已具备，2026-09-10 自底座侧移入产品侧） | 低-中（同质化；若走 ACP 接入已有客户端，差异回到治理能力） | 中高（签名分发/更新/获客） | 长 | 与治理定位的张力仍在；获客成本极高。**自建壳 vs 接入已有客户端的成本对比见 `docs/product-build-paths.md`** |

**取舍逻辑**：A 与 B 共用同一份资产（治理链 + 控制台），可组合推进（先 A 后 B）；C、D 需要重投资且丢弃差异化。

## 4. 推荐主线：分层产品化

```
L2 托管服务（远期，可选）   多租户 SaaS / 云托管运行时 · 按用量计费
        ▲
L1 企业治理增值（中期）     审计导出(SIEM/CSV) · 策略中心 · 配额与预算 · SSO/RBAC · 支持
        ▲
L0 开源底座（现在）         @node-agent-runtime/* 12 包（Apache-2.0）· 治理原语 · API 快照 · 质量门
        ▲
验证载体（非产品线）        examples/cli · examples/web · deploy/
产品侧形态候选（2026-09-10 自底座移入）  桌面端：examples/desktop-tauri · P5.1~P5.4
```

- **L0 的使命是信任与标准**：包级可消费、API 面冻结、变更可预期——这三点已在 M6 完成，属于「已经付过的成本」，现在只是激活分发（待 `NPM_TOKEN`）。
- **L1 是现金流来源**：把已经代码化的能力（脱敏、审计、限额、策略预设）包装成**合规交付物**（可导出的审计记录、可测试的策略文件、可配置的配额），而不是新造能力。
- **验证载体不是产品**（2026-09-10 底座收敛）：`examples/cli`、`examples/web`、`deploy/` 只用于验证底座能力（事件流 / 审批 / diff / 续跑 / 鉴权 / 容器交付），**不做产品级投入**。原先「控制台升级为治理工作台」的路径**撤销**：治理能力一律以**包 API + 可导出审计物**交付，界面仅在示例内顺带演进。判定与纪律见 `docs/base-convergence.md`。
- **桌面端方向（2026-09-10 自底座移入产品侧）**：底座收敛取消桌面端分类后，`examples/desktop-tauri/`、`.github/workflows/desktop.yml`、`scripts/verify-desktop.mjs`、`scripts/e2e/desktop.mjs` 与 P5.1~P5.4（实机验证 / 签名公证 / 三平台 CI / 自动更新）**整体移入产品侧**作为形态候选：代码、脚本与 CI 配置保留为产品侧资产，底座侧不再投入与判定。是否投入、以「自建桌面壳」还是「接入已有客户端（如 ACP 客户端）」形态落地，见 `docs/product-build-paths.md` 与 §8-3。
- **不做的事**：不引入运行时框架依赖（保持零依赖卖点）；不绑定单一模型厂商；不做应用层业务逻辑。

## 5. M7 里程碑草案（技术侧，待主线拍板）

## 7. 风险与反证

| 风险 | 说明 | 缓解 |
|---|---|---|
| 方向 A 获客慢 | 开源底座需要时间建信任，企业触达依赖个人网络 | 先用「治理交付包」做 3~5 个真实客户验证；控制台可演示性强，适合做冷启动素材 |
| 差异化被追平 | 大厂框架已开始补审批/沙箱（如 codex 系） | 深耕「可导出、可测试、可迁移」的合规交付细节，而非单点特性 |
| 单人产能约束 | 12 包已在维护半径边缘 | M7 优先「包装已有能力」而非新造轮子；明确拒绝 C/D 类扩张 |
| 桌面形态影响产品完整性 | 若目标客户重视桌面形态，底座侧已不再承接，需产品侧单独立项 | 主线以 Web + 容器交付为主；桌面作为产品侧可选形态，并用 `docs/product-build-paths.md` 评估「不造壳也能获得桌面/编辑器体验」的替代方案 |
| 许可决策反复 | open-core 边界一旦发布难收回 | 在实发 npm 与对外宣传前先定边界（§8-2） |

## 8. 待决策项（需要拍板）

1. **目标客户优先级**：(a) 开发者个体（重生态、轻变现）· (b) 中小团队（重体验、中变现）· (c) 企业合规场景（重审计与交付、高变现）。→ 推荐 **先 (a) 建生态、同步铺 (c) 的交付物**。
2. **商业模式**：开源影响力优先 / open-core / 交付服务 / 托管 SaaS。→ 推荐 **open-core（核心 Apache-2.0 + 治理增值闭源）**，与 §4 分层一致。
3. **桌面形态是否投入、以什么形态投入（已上收为产品侧决策）**：自建桌面壳（`examples/desktop-tauri` + P5.1~P5.4 + Apple 证书），还是走 ACP 接入已有客户端（DeepChat / Zed / JetBrains）以**免自建壳**获得桌面与编辑器形态。→ 成本与替代路径对比见 `docs/product-build-paths.md`；推荐先评估底座侧可承接的协议适配工作，形态决策可延后。
4. **是否做垂直场景**：若做，切入哪个领域、以什么形态（模板/示例/独立产品）。→ 推荐**暂不做产品，只做示例**（消解「看不懂能干什么」的获客问题）。
